### 2.1 "0/N nodes are available" format, 1.30 through 1.37

`FitError.Error()` is structurally unchanged: `0/<N> nodes are available: <PreFilter message>.` OR `<count> <reason>, <count> <reason>, ...` (sorted lexically), then optional ` <PostFilter message>` (`preemption: ...`). Since 1.31 nodes no plugin recorded get `Preemption is not helpful for scheduling`, so counts always sum to N. Reason-string changes: 1.33 PV node affinity rename and removal of spurious `no new claims to deallocate`; 1.35 taint message drops key/value; 1.37 `pod group preemption:` prefix and the preemption success message.

### 2.2 Kubelet-side rejections that look like Pending but are not

`kubelet.rejectPod` sets `phase: Failed` with `status.reason` in `OutOfcpu`, `OutOfmemory`, `OutOfpods`, `OutOf<extended-resource>`, `UnexpectedAdmissionError` (device plugin failures), `TopologyAffinityError` (Topology Manager `single-numa-node` / `restricted`), `PodOSSelectorNodeLabelDoesNotMatch`, `SupplementalGroupsPolicyNotSupported` (1.33), etc. A controller creates a replacement pod, which is the one that appears Pending. Surface the Failed sibling and its reason. Two genuinely Pending-with-nodeName cases: DRA `NodePrepareResources` failures (bound, `ContainerCreating`) and PreBind waits (volume provisioning, device binding conditions) where the pod has `nominatedNodeName` but no `nodeName`.

### 2.3 Uncertain / not shipped

Pod-level resources GA in 1.37 (code says Beta); `DRASchedulerFilterTimeout` stage (docs Alpha, code Beta); KEP-5234 mixins and KEP-5501 PreEnqueue pod status (nothing in code through 1.37); KEP-5278 and KEP-5007 planned GA 1.37 but code Beta; "KEP-5688" does not exist (the Workload API work is 4671 + 5832, 5710, 5732, 5729, 6012, 6089); DeviceTaintRule API version in 1.36/1.37 not re-verified.

## 3. What users complain about

Caveat: StackOverflow and Reddit block crawling, so frequency signals are GitHub issue-search `total_count` for exact message strings (all repos), discuss.kubernetes.io, vendor KBs (Red Hat, Broadcom, AWS, GKE, AKS) and 2024-2026 blogs. ### 3.2 Messages users say they cannot parse

- Aggregated per-node counts without node names. discuss.kubernetes.io "How do you guys debug FailedScheduling?" (Feb 2025): "it's not even showing which exact nodes are causing the issue ... it just says something vague like 'n(s) had untolerated taint,' without mentioning specific node names." The ask: "take this pending pod and point it at a specific node to see the exact reason why it's not scheduling on that node." https://discuss.kubernetes.io/t/how-do-you-guys-debug-failedscheduling/31594
- The count read as a quantity. k/k #53465: "I didn't ask for 4 CPU, I asked for 1 ... the '4' means 'I looked at 4 nodes', but the error is very misleading." https://github.com/kubernetes/kubernetes/issues/53465
- Nodes not accounted for. k/k #91340: "0/9 nodes are available: 8 node(s) didn't have free ports" with no reason for the 9th. https://github.com/kubernetes/kubernetes/issues/91340
- PreFilter errors multiplied per node. k/k #110783: "0/134 nodes are available: 134 failed to list NodeInfos". https://github.com/kubernetes/kubernetes/issues/110783
- ReadWriteOncePod wording called "misleading" (k/k #129143, Dec 2024, fixed by #129145). https://github.com/kubernetes/kubernetes/issues/129143
- The preemption suffix. Users copy "preemption: 0/1 nodes are available: 1 Preemption is not helpful for scheduling" as if it were the error; Red Hat maintains two KBs just to explain it (7020157, 7055911). https://access.redhat.com/solutions/7020157
- "didn't match Pod's node affinity/selector" covers nodeSelector and required nodeAffinity; Datadog: identical messages "requiring manual pod specification inspection." https://www.datadoghq.com/blog/debug-kubernetes-pending-pods/
- "Insufficient memory" while `top` shows free memory (RH 6987566, Broadcom 381977).
- "Insufficient nvidia.com/gpu" while nvidia-smi works; MIG nodes advertise `nvidia.com/mig-1g.10gb: 7` and `nvidia.com/gpu: 0` (gpu-operator #693, #752).
- Autoscaler messages: CA "pod didn't trigger scale-up:" with an empty reason (#4613, maintainer agreed messaging "should be clearer"); Karpenter #7839 "incompatible with nodepool ... daemonset overhead=..." with the user replying "all the resources are not being used. There is room."; #5937 "all available instance types exceed limits" during an EC2 API outage.
- Volcano #3910: "1/1 tasks in gang unschedulable: pod group is not ready" and "queue resource quota insufficient"; user: "Not sure why or how the calculation is done."
- Kueue #7433: Workload says Admitted but the pod stays SchedulingGated.
- Topology spread vs cordon (k/k #106396): users did not expect cordoned nodes to count toward skew.

### 3.3 Pending vs ContainerCreating vs ImagePullBackOff vs CrashLoopBackOff

Pod phase is Pending while containers are ContainerCreating or ImagePullBackOff, so beginners and even vendor guides call these "pending" (Komodor lists "Image Pull Errors" as Pending cause #6; groundcover: "A Pod whose containers show ContainerCreating is, at the Pod level, still in the Pending phase"). Real mixed threads: gitlab-runner #28930 (CNI sandbox), discuss 24787 (flannel), k/k #86262 (mount timeout). ResourceQuota is the inverse: pods never exist; only evidence is `FailedCreate` on the ReplicaSet. NUMA/TopologyManager rejections surface as `TopologyAffinityError` / `UnexpectedAdmissionError` on a Failed pod (k/k #84597, #112234, #123816, #128669).

What to do: check `spec.nodeName` first. If set, print "already scheduled to X; this is a kubelet/runtime problem" and route to the container state reason. If the pod does not exist, point at the owner's `FailedCreate` and namespace quota. Sources: https://komodor.com/learn/pod-in-pending-state-top-6-causes-and-how-to-resolve/ , https://www.groundcover.com/learn/kubernetes/containercreating-status , https://gitlab.com/gitlab-org/gitlab-runner/-/issues/28930 , https://notes.kodekloud.com/docs/Kubernetes-Troubleshooting-for-Application-Developers/Troubleshooting-Scenarios/Case-of-the-Missing-Pods/page

### 3.4 Bare-metal / on-prem specifics

- Single-node control-plane taint: kubeadm (k/k #116133), k3s `k3s-controlplane=true:NoExecute` and `CriticalAddonsOnly` (#1401, k3d #430), Talos `allowSchedulingOnControlPlanes` (#6200), Docker Desktop (discuss 18112), minikube `not-ready` taint from uninitialized CNI (#14924).
- k3s scheduler silence: all pods Pending with `Events: <none>` after version mismatch (#4864) and after 1.27 upgrade via watch starvation (k/k #123448).
- local-path-provisioner: PV nodeAffinity pinned to a hostname that changes (#68), PVC bound before scheduling then node lacks CPU (#509).
- OpenShift: infra/master taints (RH 7034799, 7127508), namespace `defaultNodeSelector` (5676721), volume zone vs MachineSet (7128284), maxPods via KubeletConfig (7003920).
- GPU operator: 8-component chain (NFD, driver, toolkit, device plugin, GFD, DCGM, MIG manager, validator); any failure leaves allocatable 0 (#752, #442, #1845); mixed MIG + full GPU nodes hang Pending with R570 drivers; both `nvidia.com/gpu` and MIG profiles advertised (#637).
- Hugepages must be preallocated and vanish after reimage (k/k #80576).
- SR-IOV: device plugin snapshots VFs at startup; VFs created later are not advertised (#276, #223, #151).
- MetalLB and Rancher did not surface as Pending causes.

### 3.5 Surveys

No published survey quantifies pending pods as a top-N issue. ## 5. Recommendations (ranked by expected user value)

1. **Triage before predicates: catch the "not actually a scheduling problem" cases first.** Check `spec.nodeName` (bound means kubelet/runtime: ContainerCreating, FailedMount, FailedCreatePodSandBox, ImagePullBackOff, DRA NodePrepareResources), `spec.schedulingGates` (print gate names and the owning manager from managedFields; for Kueue show Workload admission), Failed siblings with `OutOf*` / `TopologyAffinityError` / `UnexpectedAdmissionError`, and the owner's `FailedCreate` quota events when the pod does not exist. Rationale: section 3.3 shows vendors themselves conflate these, K8sGPT's Pod analyzer is the only tool that partially does it, and it is cheap. Sources: groundcover, Komodor, k/k #84597, #128669, kueue #7433.

2. **Per-node verdict table with named nodes and the single decisive predicate, plus a "closest node and what would have to change" line.** The single most-quoted complaint is that `0/N nodes are available` hides node names (discuss 31594, k/k #91340, #53465). Add fragmentation detection ("total free 12 CPU but no single node has 4"), largest-request-no-node-fits, and fitcheck-style buckets (rejected / would-fit-if / initializing). Borrow kube-capacity's `--available` table layout since users already read it.

3. **Stable `-o json` with a versioned schema, a `SKILL.md`, and an optional `mcp` stdio subcommand.** Every AI tool surveyed (K8sGPT, HolmesGPT, kubectl-ai, kagent, kubernetes-mcp-server, Flux159) bottoms out at `kubectl describe`; a deterministic backend is the gap. Precedents: kubectl-ai `--mcp-server`, k8sgpt `serve --mcp`, HolmesGPT remote MCP config. Do JSON and SKILL.md first (near-zero maintenance, works in Claude Code / Codex / Gemini CLI / Cursor), MCP third. Sources: agentskills.io, k8sgpt MCP.md, holmesgpt.dev.

4. **Model the 1.35 to 1.37 scheduler surface before it bites: gang scheduling, NNN semantics, DRA extended-resource mapping.** Concretely: read `pod.spec.schedulingGroup.podGroupName` and print the PreEnqueue holds (`waiting for pods's pod group ... to appear`, `minCount (N) cannot be satisfied: S scheduled, R remaining`), priority and schedulerName mismatch with the PodGroup; treat `status.nominatedNodeName` as "preemption in progress / PreBind wait / external hint", never as "will schedule"; do not print `Insufficient vendor/gpu` when a DeviceClass `extendedResourceName` maps it (GA 1.37); model NodeDeclaredFeatures (GA 1.37) and `CSIDriver.preventPodSchedulingIfMissing` (beta 1.37). Detect the cluster minor and say which features the binary models. Sources: section 2, kubernetes.io gang-scheduling and podgroup-scheduling docs, v1.37 DRA blog.

5. **Finish the DRA story where nobody else is: device taints GA, partitionable counters, consumable capacity, binding conditions.** kubectl-view-allocations (807 stars, active) covers GPU extended resources but not ResourceClaims; kubectl-can-schedule runs the DynamicResources plugin but has no post-hoc claim-status view. Print per claim: allocation state, DeviceClass existence, matching ResourceSlices (skip incomplete pools), counters consumed across the pool, device taints vs claim tolerations (incl. DeviceTaintRule), binding-condition waits with timeout, and `filterTimeout` hits. This is the defensible niche.

6. **On-prem and GPU heuristics with named fixes.** Single-node control-plane taint (print both fixes: toleration vs untaint; recognize k3s `CriticalAddonsOnly`, Talos, minikube `not-ready` from CNI); allocatable 0 for the requested extended resource means "device plugin has not advertised it on this node" with the device-plugin pod state; MIG name mismatch (`nvidia.com/mig-*` advertised, `nvidia.com/gpu` requested); hugepages not preallocated or non-multiple request; SR-IOV VF snapshot ordering; local-path PV pinned to a renamed hostname; OpenShift namespace `defaultNodeSelector`. Sources: section 3.4, gpu-operator #693/#752, k/k #80576, local-path-provisioner #68, RH 5676721.

7. **Scheduler-silence and staleness detection.** If there are zero `FailedScheduling` events and `schedulerName` is default, check the kube-scheduler pod / lease and print "the scheduler has not attempted this pod"; if `schedulerName` is custom, say so. Always print the age of the last FailedScheduling event and warn that the message can lag a fixed cluster by up to the 5-minute unschedulable flush. Sources: k3s #4864, k3s discussion #10044 (k/k #123448), k/k #104521, KEP-4247 queue semantics.

8. **Translate, do not reimplement, autoscaler output.** When Karpenter or Cluster Autoscaler is present, surface their pod events verbatim (`NotTriggerScaleUp`, `incompatible with nodepool`, `daemonset overhead`), NodePool limits vs `status.resources`, and the CA status ConfigMap; explain "wouldn't fit if a new node is added". Stay silent when neither exists so bare-metal output remains clean. Sources: karpenter.sh troubleshooting, autoscaler FAQ, #4613, #7839.

9. **Stability engineering: version pinning policy, kind matrix, golden JSON tests.** Pin `k8s.io/kubernetes` to the newest minor, generate the replace block by script, run a kind matrix N-2 minors behind, golden-test `-o json` (color off), isolate scheduler imports in one package, and publish a compatibility matrix in the README (scheduler-plugins' one-release-line-per-minor policy is the honest model). Print a warning when the cluster minor differs from the compiled minor since predicate behavior changed in 1.33, 1.35 and 1.37 (message renames, taint operators, PodGroup). Sources: scheduler-plugins RELEASE.md, kube-scheduler-simulator go.mod, kind releases, int128/kubectl-tree-e2e-test.

10. **Distribution and UX polish, then positioning.** UX: `--color auto|always|never` + `NO_COLOR` + isatty; opt-in `--exit-code` (kubent model: 0 by default, distinct non-zero when still Pending, for CI gates); `version` subcommand with commit/date; `kubectl_complete-why_pending` shim via a Homebrew tap formula (krew cannot ship it; issue #812). Distribution: goreleaser + `.krew.yaml`, a Homebrew tap, GitHub topics `kubectl-plugin` / `krew-plugin`, a PR to awesome-kubectl-plugins, Artifact Hub is automatic, KubeWeekly form, a k9s plugin snippet in the README, and a kubernetes.io or CNCF blog post framed as "how the scheduler decides, illustrated" rather than a product launch (Headlamp's precedent). Positioning: state in the README that kubectl-can-schedule is pre-deploy fit checking and why-pending is post-hoc per-pod diagnosis, and note the unrelated cilasbeltrame/kubectl-why-pending repo (krew resolves `why-pending` to yours). Sources: section 4, krew best-practices, no-color.org, kubent README, kubectl-cnpg formula.

Honest caveats on expected value: items 1, 2 and 7 address the highest-frequency confusions found and are cheap; items 4 and 5 are where competition is thinnest but user volume today is small (DRA "cannot allocate all claims" appears in only 51 GitHub issues, PodGroup is beta-off in 1.37), so they are a bet on 2027 GPU clusters rather than current demand; item 3 is the biggest reach multiplier but only if the JSON schema stays stable. No survey quantifies pending pods as a top issue, so adoption ceiling for a single-purpose plugin is probably in the kube-capacity / view-allocations band (hundreds to low thousands of stars), not kubectx territory.
